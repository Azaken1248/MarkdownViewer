# Contributing

The conventions here are specific and mostly unwritten, which is the reason
for this file. None of it is style for its own sake; each one exists because
something went wrong without it.

## Before you start

```bash
npm install
npm test
```

Node 20 or newer (`.nvmrc` pins 20; CI runs 20 and 22). The suites start real
servers against temporary directories, so they never touch your own documents.

## The three commands that must pass

```bash
npm test
npm run lint
npm run typecheck
```

CI runs all three, plus `npm audit`, `npm run audit:cdn` and a build. A change
that fails any of them is not finished.

## Tests

**Anything a test could catch, a test should catch.** The suite is thorough
enough that people trust it, which means the gaps are where confidence exceeds
evidence.

- Put a new check in the suite that already covers that area. `npm test <suite>`
  runs one; `npm test <suite> -- --only "some text"` narrows the output.
- **Watch a new test fail.** Break the behaviour it covers, confirm the check
  goes red, then put it back. A test that has only ever passed has not been
  shown to test anything.
- Assert the behaviour, not the implementation. Several suites read the source
  and assert on its shape; those exist to hold a structural decision in place,
  and each says so in a comment. Prefer a check that would survive a rewrite.
- `npm run coverage` writes a map of what nothing reaches. Use it as a map, not
  as a target.

## Complexity

`npm run lint` warns about a function that is too long, too branchy, too deeply
nested or takes too many arguments. The budget for those warnings is **zero**,
pinned by the `limits` suite.

Raising a limit is allowed. It is a change to `test/limits.test.js` in a commit
that says why, not a number that drifted.

## Markup

`innerHTML` built out of a value is refused by the linter. Where interpolation
is right, use the `html` tagged template in `public/js/dom-html.js`, which
escapes every interpolation:

```js
node.innerHTML = html`<i class="ph ${icon}"></i><span>${label}</span>`;
```

Markup that is already safe for a reason of its own assigns directly with an
`eslint-disable-next-line` and **a comment above it naming the reason**. The
`headers` suite fails on an opt-out with no reason.

## Writing it down

Comments explain why, not what. The code says what it does; a comment earns its
place by saying what the next person would otherwise have to work out — the
constraint that forced this shape, the thing that was tried and did not work,
the failure that produced the rule.

Documentation lives in `docs/`. The README is the front door and stays short:
what it is, how to run it, where everything else is.

## Commits

- **One change per commit.** A refactor and a fix are two commits.
- **A prose subject line**, describing what changed, in plain words. Look at
  `git log --oneline` for the register. Not a conventional-commits prefix, not
  a ticket number.
- **A body that says why**, when the why is not obvious from the diff. The
  interesting part is usually what was wrong before.
- **No attribution trailers.** No `Co-Authored-By`, no generator footers. The
  history has none and stays that way.

## What never gets committed

- Runtime state: `data/`, `assets/`, `deleted_markdowns/`, `public/docs/`.
  These are somebody's documents and accounts.
- `public/build/` — regenerated by `npm run build`.
- Working notes, plans and review documents. Keep them out with
  `.git/info/exclude` rather than `.gitignore`, which is shared.
- Anything with a credential in it.

`package-lock.json` **is** committed. It is what makes `npm ci` reproducible.

## Dependencies

The runtime surface is four packages and is kept that small deliberately. A new
one needs a reason that outweighs being another thing to keep patched.

Libraries loaded from a CDN are pinned to an exact version with a subresource
integrity hash. Changing one means changing both — `npm run audit:cdn` verifies
each file against its hash and checks every pinned version against the advisory
database, and it runs in CI.

ESLint and its plugins are pinned to exact versions, because a major version of
a linter changes what CI accepts without anybody changing a line of source.

## Security

Do not open a public issue for a vulnerability. See [SECURITY.md](SECURITY.md).
